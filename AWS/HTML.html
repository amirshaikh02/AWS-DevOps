★ 1. Core idea — Edge services

Edge services place DNS, delivery, and filtering closer to the internet-facing side of the application. The goal: process traffic before it reaches the main application. The Region hosts the heavy resources; the edge is a lightweight, distributed layer that handles everything the user touches first.

Why this matters: Without edge security, malicious traffic hits your ALB and EC2 directly. That consumes bandwidth, CPU, and connection slots. By filtering at the edge, you protect the expensive application tier and keep the experience fast for legitimate users.
🌍 2. AWS Cloud at the edge — full breakdown

🏢 REGION

What: Geographic area with 2+ Availability Zones. Contains compute (EC2), storage (S3, EBS), databases (RDS), and networking.

Why: This is the central hub — it runs the real workload. It is not at the edge. Everything that needs persistence or heavy compute lives here.

Example: us-east-1, eu-west-1.

📍 EDGE LOCATION

What: 400+ globally distributed data centers operated by AWS.

Why: Reduces latency for CloudFront caching, Route 53 DNS resolution, and WAF/Shield filtering. Users hit the nearest edge, not the far-away Region.

Example: A user in Mumbai hits a Mumbai edge instead of the Oregon Region.

🏘️ LOCAL ZONE

What: A mini-Region extension inside a metro area, connected to the parent Region.

Why: Ultra-low latency (single-digit ms) for workloads like real-time gaming, live streaming, AR/VR, and analytics.

Example: AWS Local Zone in Los Angeles for a Hollywood video editing workload.

📦 OUTPOSTS

What: Physical AWS racks installed inside your data center.

Why: Data residency laws, low-latency on-prem applications, hybrid cloud strategy. AWS manages the hardware, you use AWS APIs.

Example: A hospital keeps patient data on Outposts to meet compliance.

❄️ SNOW

What: Portable, rugged edge devices — Snowcone, Snowball Edge, Snowmobile.

Why: Migrate petabytes of data offline, run compute in disconnected environments (military, ships, oil rigs).

Example: A film crew uses Snowball Edge to process 4K footage in the field.

Key insight: Edge is a spectrum, not one thing. It spans from hyperscale CDN (CloudFront) to regional extensions (Local Zones) to fully offline devices (Snow). For web applications, the most common "edge" layers are CloudFront + Route 53 + WAF + Shield.
🌐 3. Route 53 — DNS explained

Route 53 answers: “Where should this name go?” It is the first stop for every request and can also act as the first layer of routing intelligence.

👤 USER example.com
→
📒 ROUTE 53 hosted zone
→
🎯 ENDPOINT ALB / CF

📋 DNS flow — step by step

  1. Client query: The browser asks a recursive resolver for example.com.
  2. Recursive lookup: The resolver walks the DNS tree — root → .com → example.com.
  3. Authoritative answer: Route 53 returns the A record (or alias) with a TTL.
  4. Caching: TTL (e.g., 300s) means resolvers and browsers remember the answer until it expires.
  5. Routing logic: Health checks + routing policy determine the actual answer returned.

Why Alias records matter: Unlike CNAME, Alias records work at the root domain (example.com, not just www.example.com) and point directly to AWS resources like ALB or CloudFront. They are also free and support health checks.
🎤 INTERVIEW: Route 53 = DNS + routing. ALB = request distribution. They solve different problems — Route 53 picks the destination, ALB spreads requests across targets behind that destination.
🧭 4. Route 53 routing policies — deep dive

🔹 SIMPLE

What: Single record, one answer. No health checks.

When: Basic web app with one endpoint.

⚖️ WEIGHTED

What: Split traffic by relative weights (e.g., 90/10).

When: Canary releases, blue/green deployments, A/B testing.

⚡ LATENCY

What: Routes to the Region with the lowest latency for that user.

When: Multi-region apps where speed is the priority.

🔄 FAILOVER

What: Active-passive. Primary answers if healthy; standby answers if not.

When: Disaster recovery (DR) setups.

🌎 GEOLOCATION

What: Routes based on the user's country or continent.

When: Compliance (EU data stays in EU), localized content.

📏 GEOPROXIMITY

What: Routes by distance + a "bias" you can shift (e.g., -100 to +100).

When: Fine-tune traffic distribution across regions.

🔀 MULTI-VALUE

What: Returns up to 8 healthy records in one DNS answer.

When: Client-side load balancing, high availability.

📡 IP-BASED

What: Routes based on the client's CIDR block.

When: Route specific corporate networks to specific endpoints.

💡 Quick mapping: Percentage → WEIGHTED · Primary+standby → FAILOVER · Fastest → LATENCY · Country → GEOLOCATION · Several healthy → MULTI-VALUE
Common mistake: Confusing LATENCY with GEOPROXIMITY. LATENCY is measured network latency (AWS decides). GEOPROXIMITY is geographic distance with a manual bias (you decide). LATENCY is simpler; GEOPROXIMITY is more flexible.
⚖️ 5. Weighted & Multi-Value routing — in detail

📊 WEIGHTED routing

How it works: Each record gets a weight (0–255). Route 53 returns records proportionally. 90:10 means ~90% of DNS answers go to the first record.

Caveats: DNS caching means observed traffic may not match the exact ratio. Use low TTL during migrations.

Common use: Canary release, blue/green migration, regional migration, controlled testing.

EXAMPLE: Old prod = 90 · New prod = 10. Increase the new environment gradually after health checks pass.

🔀 MULTI-VALUE routing

How it works: Route 53 returns up to 8 healthy values. The client (browser or app) picks one — often the first, but apps can retry.

Key: Only healthy records are returned when health checks are configured.

Important: This is DNS-level, not ALB-level. The client picks, not a load balancer.

🧠 MEMORY: Weighted = “how often?” / Multi-value = “which healthy answers together?”
When to use which? Use WEIGHTED when you want a controlled split (e.g., 10% to new). Use MULTI-VALUE when you want resilience — if one endpoint fails, clients can still reach the other healthy ones. Multi-value is not a replacement for a load balancer; it's a DNS-level redundancy mechanism.
💥 6. DDoS + OSI layers — deep dive

🎯 What happens in a DDoS attack?

DDoS = many distributed sources → one target. Attackers use botnets (compromised IoT devices, servers, PCs) to overwhelm the target.

The goal: Exhaust one of four resources:

  • Bandwidth — saturate the network pipe
  • Connections — fill the connection table
  • Protocol resources — exhaust TCP/UDP state
  • Application resources — CPU, memory, DB connections

Defense layers: Edge capacity → Shield → WAF → ALB → Multi-AZ capacity.

📚 OSI layers + DDoS — know the layer → understand the attack

6PresentationSSL/TLS abuse

L3/L4 (Network + Transport): UDP reflection, SYN floods. Think infrastructure resource exhaustion. Example: a SYN flood sends millions of TCP SYN packets, filling the connection table so real users can't connect.
L7 (Application): HTTP floods and DNS query floods. Think request/service resource exhaustion. Example: an HTTP flood sends legitimate-looking GET requests to a login page, consuming app CPU and DB connections.
⚠️ Note: Not every DDoS attack is an HTTP attack. WAF is useful for web/application request inspection. Shield provides managed DDoS protection; capabilities depend on the protection level.
🛡️ 7. AWS Shield — detailed

Managed DDoS protection for AWS applications. Shield is always-on and automatically protects against common infrastructure-layer attacks.

🟢 SHIELD STANDARD

What you get: Automatic, baseline DDoS protection for all AWS customers at no extra cost.

Protects against: Common L3/L4 attacks — SYN floods, UDP reflection, ICMP floods.

Applies to: CloudFront, Route 53, ALB, ELB, Global Accelerator.

Best for: Every AWS customer — it's on by default.

🔵 SHIELD ADVANCED

What you get: Enhanced protection + 24/7 access to the DDoS Response Team (DRT).

Adds:

  • Cost protection (refunds for scaling during attack)
  • Advanced real-time metrics and alarms
  • Proactive engagement from AWS during attacks
  • WAF included at no extra cost

Best for: Business-critical apps where downtime costs money.

Attack types Shield protects against:

L7 – HTTP floods / DNS query floods L6 – SSL abuse L4 – SYN floods L3 – UDP reflection
Shield vs Shield Advanced — real difference: Standard is a filter. Advanced is a filter plus a team, a wallet, and visibility. When you're under a large attack, the DRT can manually tune your WAF rules and engage AWS's scrubbing capacity on your behalf.
🛡️ SHIELD + WAF: Shield protects the network (L3/L4) and absorbs volumetric attacks. WAF protects the application (L7) and filters malicious requests. Together they form a layered DDoS defense.
🧱 8. AWS WAF — Web Application Firewall

WAF asks: “Should this HTTP/HTTPS request be allowed?” It operates at Layer 7 and inspects the actual request — headers, body, URI, query string, IP, and more.

❌ BLOCK

🧩 WAF building blocks

  • Web ACL – the policy container. Defines default action (allow or block).
  • Rule – condition + action. E.g., "if URI = /admin AND IP not in whitelist → BLOCK".
  • IP Set – a reusable list of IPs/CIDRs (e.g., blocked IPs).
  • Regex Set – pattern matching on request components.
  • Rule Group – a reusable bundle of rules.
  • Logging – send request details to Kinesis, S3, or CloudWatch.
  • Metrics – CloudWatch metrics for rule matches.

⚙️ Rule actions

Allow = let the request pass. Block = deny with a 403. Count = observe without blocking (for testing).

Best practice: Start in COUNT mode. Watch logs for a week. Then move to BLOCK once you're confident there are no false positives.

EXAMPLE RULE:
IF URI = /login
AND rate > 100 req/5min from same IP
AND IP matches risky set
THEN → BLOCK
Where WAF attaches: CloudFront distributions, ALB, API Gateway, AppSync, Cognito. It does not attach to EC2 directly — you put it in front of the entry point.
📋 9. WAF rule statements + logging

Rule statements combine conditions to describe what should be filtered. They are the vocabulary of WAF rules.

🛡️ ATTACK PREVENTION

  • SQL injection — pattern detects SQL keywords in inputs.
  • XSS — detects script tags and injection patterns.
  • Managed rules — AWS-maintained rule sets (AWSManagedRulesCommonRuleSet, etc.).

📡 TRAFFIC FILTERING

  • Rate limiting — e.g., 2000 requests per 5 minutes per IP.
  • IP/CIDR — allow/block specific IP ranges.
  • Geo — allow/block countries or continents.

🔎 PATTERN MATCHING

  • Regex — custom patterns on URI, headers, body.
  • String — exact substring matches.
  • Size — e.g., block bodies > 8KB (a common attack vector).

🧠 LOGICAL

  • AND — all conditions must match.
  • OR — any condition can match.
  • NOT — exclude specific matches (e.g., NOT internal IP).

📊 Logging & visibility

🔥 Kinesis Firehose

Stream logs in near real-time for analytics.

📦 S3

Long-term archive for compliance and forensics.

📊 CloudWatch

Metrics + logs for dashboards and alarms.

Why log? You need to see which rules matched, from which IPs, and how often. Without logs, you're blind — you can't tell if a rule is catching real attacks or blocking real users. Always test in COUNT before BLOCK.

1. DNS

Route 53 selects the endpoint using the configured routing policy. Health checks remove unhealthy targets.

2. EDGE

CloudFront delivers/caches content close to users, absorbing traffic far from the origin.

3. SECURITY

Shield helps with DDoS; WAF filters web requests. Both run at the edge.

4. RESILIENCE

ALB + Auto Scaling + multiple AZs distribute application capacity and survive AZ failures.

Why this order matters: By the time traffic reaches the ALB, malicious requests have already been filtered by WAF, volumetric attacks have been absorbed by Shield + CloudFront, and routing has been intelligently handled by Route 53. The Region only sees clean, legitimate traffic.

📌 Use cases

  • Many accounts/resources: Central policy reduces manual configuration across 100s of accounts.
  • Continuous app creation: New apps automatically inherit the security baseline.
  • Central visibility: Security team sees threats across the whole org.
  • Manages: WAF, Shield Advanced, Security Groups, Network Firewall.

⚠️ Manager ≠ Firewall

Firewall Manager is a policy management service. It doesn't inspect traffic itself.

The underlying services — WAF, Shield, Security Groups, Network Firewall — do the actual filtering and protection.

Analogy: Firewall Manager is the policy author. WAF is the police officer enforcing it.

Example scenario: Your security team defines a WAF policy in Firewall Manager: "All ALBs in all accounts must have the AWSManagedRulesCommonRuleSet attached." Firewall Manager auto-deploys this across every account. When a new app is created, Firewall Manager attaches the Web ACL automatically — no manual work, no gaps.

🔐 13. Public vs private — draw the boundary

A common interview question: where should the application servers live? Answer: never directly on the internet.

👤 USER
→
☁️ CF
→
🧱 WAF
→
⚖️ ALB public

🌐 PUBLIC SUBNET

What: A subnet with a route to an Internet Gateway.

What lives there: Internet-facing components — ALB, NAT Gateway, bastion hosts.

Example: ALB that receives traffic from CloudFront.

🔒 PRIVATE SUBNET

What: A subnet with no direct route to the internet.

What lives there: Application tier — EC2 (AZ-A, AZ-B) — and database tier — RDS.

Outbound internet: Use NAT Gateway when private resources need outbound access (e.g., patch downloads).

Why this matters: If EC2 is in a public subnet, an attacker can hit it directly — bypassing WAF, Shield, and CloudFront. By keeping EC2 private and only exposing the ALB, every request must pass through the full edge security stack first.
INTERVIEW RULE: Typical 3-tier design keeps app and DB in private subnets; only the load balancer is in a public subnet. Always mention the public/private boundary — it shows you understand security best practices.
⚖️ 14. Shield vs WAF — do not mix them

They work together, but they solve different security problems.

🛡️ SHIELD

Primary focus: DDoS detection / mitigation

Scope: Network / transport + application

Question: “Is this a DDoS event?”

Protects against: SYN floods, UDP reflection, HTTP floods (Advanced).

Managed by: AWS automatically (Standard) or with DRT (Advanced).

🧱 WAF

Primary focus: Web request inspection

Scope: HTTP/HTTPS (Layer 7)

Question: “Should this web request be allowed?”

Rules: IP, rate, regex, managed rules.

Managed by: You — you write the rules.

🧠 MENTAL MODEL: Shield → “Is this a DDoS event?” · WAF → “Should this request be allowed?” · ALB/CF → “Where should allowed traffic go?”
Common interview trap: “Can WAF stop a SYN flood?” — No. SYN floods are L4; WAF is L7. Shield handles L4. WAF handles L7 HTTP floods. Know the layer, know the tool.
